# 题库重构参考沉淀

> 记录时间：2026-09-01  
> 目的：把朋友题库系统截图与 AI 录入流程中的关键信息沉淀下来，作为后续 MathCyclus 题库存储结构、录入流程、专题组织、图片附件系统和数据库重构的长期参考。  
> 约束：本文档只做方案沉淀，不代表已经修改当前代码；后续真正改造时应先确认存储模型，再逐步迁移功能。

---

## 1. 总体观察

朋友的题库系统不是单纯的“文件浏览 + 编辑器”，而是更接近一个带有明确业务对象的题库管理系统。它把题目拆成了多个维度：题目本体、答案、解析、阅卷数据、易错警示、考查目的、命题过程、试题评析、参考文献、试卷来源、题号、小题、题型、专题模块、专题分组等。

这给我们的启发是：未来题库不能继续完全依赖“文件路径 + 文件名 + 文件内容”来表达全部信息。当前 MathCyclus 的 `.tex` 文件方案足够灵活，也便于直接编辑，但当需求扩展到批量录入、跨试卷复用、专题组织、图片附件、AI 规范化、版本追踪、批量校验和组卷统计时，就需要引入更稳定的数据层。

一个合理方向是：

- 保留 `.tex` 作为可读、可导出、可人工修订的内容格式。
- 引入稳定 `question_id` 作为题目身份，不再让文件路径承担唯一身份。
- 把题目内容、元数据、试卷关系、专题关系、附件资源、导入批次、修订记录分开。
- AI 录入不直接“盲写库”，而是先解析、校验、生成报告，再批量确认写入。
- 图片与非 TikZ 图形不要急着硬塞进现有 `.tex`，应等新存储模型确定后以附件表/资源目录方式挂接到题目。

## 2. 朋友系统的页面模块

截图中朋友的首页标题为“高中数学题库 工作台”，功能卡片包括：

| 模块 | 状态 | 说明 |
| --- | --- | --- |
| 录入试卷试题 | 可用 | 面向高考试卷、模拟卷等有明确年份和题号的题目录入 |
| 录入专题 | 可用 | 面向专题、模块、小专题、分组的题目组织 |
| 录入课本习题 | 未来更新 | 面向教材章节、课本题号、练习题体系 |
| 解除试卷试题链接 | 未来更新 | 用于处理题目与试卷之间的关联关系 |

这说明他的系统从一开始就区分了三类来源：

1. **试卷题目**：强依赖年份、试卷名、题号。
2. **专题题目**：强依赖模块、专题、分组。
3. **教材习题**：强依赖教材版本、章节、页码、题号。

对我们后续重构的启发是：不要把“知识板块/年份/文件”当成唯一组织方式。它可以继续作为一种视图，但底层应该支持多种组织关系。

## 3. 录入试卷试题页面字段拆解

朋友的试卷题目录入页面提供了非常多的字段，整体可以分为“操作工具栏”“题目定位”“题目内容”“扩展说明”四类。

### 3.1 操作工具栏

截图中可见的按钮包括：

- `试题格式化`
- `检查`
- `编译 LaTeX`
- `复制到剪切板`
- `排版规范检查`
- `清空`
- `确定并导出`
- `仅导出 tex`
- `删除`

这些按钮反映了一个完整录入链路：

1. 输入原始内容。
2. 格式化为统一题库规范。
3. 检查字段与语法。
4. 编译 LaTeX 或进行 KaTeX/TeX 预览验证。
5. 支持复制和导出。
6. 最终确认入库或删除。

对我们当前项目的启发：

- “录入新题”不应只是一个文本框和保存按钮，未来应该区分：
  - 原始输入区
  - 规范化结果区
  - 预览区
  - 校验结果区
  - 入库确认区
- AI 生成或 OCR 识别后，必须经过“格式化/检查/预览/确认”四步，不宜直接写入正式题库。

### 3.2 题目定位字段

左侧“题目定位”区域包含：

- 年份
- 题源
- 题号
- 题号（文）
- 小题
- 题型编号
- 考查目的
- 命题过程
- 试题评析
- 参考文献

这些字段的意义：

- `年份`、`题源`、`题号`、`题号（文）`、`小题`用于把题目定位到具体试卷位置。
- `题型编号`对应题型字典，类似单选、多选、填空、解答等。
- `考查目的`、`命题过程`、`试题评析`属于教研分析字段，不是题干本身。
- `参考文献`用于保留来源说明或后续导出引用。

对我们当前项目的启发：

- 当前 `.tex` 元数据里已有 `难度星级`、`标签`、`备注`、`组卷引用次数`，但缺少更严肃的试卷定位字段。
- 未来应把“试卷位置”放入关系表，而不是只写进题干 `\origin{...}` 或文件名。
- 文理卷同题号、同题不同卷、同题多源出现时，需要用关联表表达，而不是复制多个文件。

### 3.3 题目内容字段

右侧主要内容字段包括：

- 题干
- 答案
- 解析
- 阅卷数据
- 易错警示

其中“答案”旁还有一个勾选项，底部有 `不覆盖`、`确定后清空` 等选项。

这些字段表明朋友系统把“答案”和“解析”明确区分，并且还额外保存“阅卷数据”和“易错警示”。这比我们当前仅按 `problem`、`answer`、`solutions` 三段更细。

建议未来字段分层：

| 层级 | 字段示例 | 说明 |
| --- | --- | --- |
| 核心题目 | 题干、选项、答案、解析 | 组卷和展示必需 |
| 教研分析 | 考查目的、命题过程、试题评析 | 面向教研、命题、复盘 |
| 教学辅助 | 易错警示、阅卷数据、方法提示 | 面向讲解、错题归因 |
| 来源证据 | 官方标记、参考文献、原始来源文本 | 面向可信度和追溯 |

## 4. AI 批量录入流程信息

朋友与 AI 沟通的批量录入任务非常有参考价值。核心目标是从原始题目 `.tex` 文件和解答 `.tex` 文件中批量导入或更新数据库。

### 4.1 原始路径与文件范围

最初提到的路径类似：

- `CodexProjectGaokao/GaokaoWeb/2010/2010{题集名称}.tex`

后来确认实际路径是：

- `D:\CodexProjectGaokao\LaTeX\2010\2010{题集名称}.tex`
- 解答文件可能位于：`D:\CodexProjectGaokao\LaTeX\2010s\sol2010{题集名称}.tex`

这一批共有 43 个 `2010*.tex` 文件。用户要求不是直接全量跑，而是：

1. 先测试一个文件：`2010AnaGeoAdvanced.tex`。
2. 测试稳定后再处理全部文件。
3. 全量前必须列出所有源试卷名称与数据库试卷名称的映射表。

对我们的启发：

- 批量导入必须有“试跑模式”。
- 批量导入必须有“映射确认阶段”。
- 不应假设源文件名与数据库中试卷名完全一致。

### 4.2 导入前检查规则

朋友系统要求导入前检查：

1. 如果试卷不存在，暂时跳过。
2. 如果试卷存在但题目不存在，则插入题目。
3. 如果试卷存在且题目存在，并且现有更新日期为 `2025-02-17`，则允许更新规范化字段。
4. 如果题目更新日期晚于 `2025-02-17`，则不更新，但写入报告。

这个规则背后非常重要：**批量脚本不能覆盖人工后续修订过的题目。**

对我们的启发：

- 未来需要 `created_at`、`updated_at`、`normalized_at`、`last_manual_edit_at` 等时间字段。
- 如果只有 `updated_at`，也可以临时作为“录入时间”代理，但这不是长期最优设计。
- 批量 AI 更新必须保护人工修改。
- 所有跳过、覆盖、失败都要进入报告。

### 4.3 规范化字段范围

AI 询问了规范化范围，最终确认只规范化以下字段：

- 题干
- 选项 A~E
- 答案
- 答案解析
- 考查目的
- 命题过程
- 试题评析
- 阅卷数据
- 易错警示

不应随意改动：

- 原始 `.tex` 文件
- 官方标记
- 原始参考文献信息
- 不确定的特殊选项排版

对我们的启发：

- AI 规范化应有白名单字段。
- 原始输入必须保留，规范化输出另存。
- 对于复杂表格选项、特殊图形、无法稳定解析的题，应标记为“待人工确认”，而不是强行修复。

### 4.4 参考文献与官方标记

确认规则：

- `官方` 标记从解答文件进入 `Question.官方` 字段。
- `\cite{...}` 保留在 TeX 正文中，不解析成参考文献字段。
- 未来导出时可以考虑把参考文献字段转换为 `\cite{参考文献字段}`。

对我们的启发：

- “正文中的引用命令”和“结构化参考文献字段”应区分。
- 不要在导入阶段过度解释来源文本。
- 对于官方答案、民间解析、AI 生成解析，应有来源类型字段。

## 5. 专题录入与分组机制

朋友系统的“录入专题”页面显示了一个非常清晰的专题组织模型：

> 大专题（Module）→ 小专题（Topic）→ 分组（Group）→ 题目

### 5.1 专题信息字段

页面中的“专题信息”包括：

- 已有模块复选框：
  - 高中预备知识
  - 函数
  - 三角学
  - 立体几何
  - 解析几何
  - 概率与统计
  - 算法
  - 数学建模
  - 新定义
  - 开放性问题
- 新模块输入
- 目录选择
- 专题名称
- 文件名
- 简介
- 已有专题下拉选择
- 操作按钮：
  - `+ 模块`
  - `载入`
  - `保存专题`
  - `清空`

这说明专题不是简单标签。专题具有：

- 所属模块
- 专题名称
- 文件名或导出名
- 描述
- 题目列表
- 分组结构

### 5.2 专题题目列表

题目列表支持：

- 通过 `qid` 添加题目。
- 通过试卷信息添加题目：
  - 年份
  - 试卷名
  - 不含年份
  - 题号
  - 题号（文）
  - 小题
  - 检查
- 表格列包括：
  - `#`
  - `题目编号`
  - `出处`
  - `题干`
  - `分组名称`
  - `备注`
  - `删除`

另一个截图显示专题列表支持：

- `批量录入`
- `新增分组`
- 当前分组选择，例如 `A组`
- 删除分组
- 每道题可填写备注

对我们的启发：

- “标签”适合轻量分类，但“专题”应该是独立业务对象。
- 一个题目可以属于多个专题。
- 一个题目在不同专题中可以有不同备注、不同排序、不同分组。
- 专题内排序不应该写回题目本体，而应写在 `TopicQuestion` 关系中。

## 6. 数据库结构启发

朋友系统使用 SQL Server 2024。截图中提到的核心表包括：

| 表 | 作用 |
| --- | --- |
| `Math.Question` | 存储题目本体，包括题干、答案、解析、分析字段等 |
| `Math.Paper` | 存储试卷名称、年份、试卷元信息 |
| `Math.PaperQuestion` | 连接题目与试卷，记录某题出现在某试卷的哪个题号/小题 |
| `Math.ExType` | 题型编码与题型名称，较少更新 |

核心关系：

- 一个题目可以出现在多张试卷中。
- 一张试卷包含多道题。
- 题目与试卷的题号、文理题号、小题等信息应放在 `PaperQuestion` 中。
- 题型字典独立维护。

这对我们非常关键，因为当前文件式题库天然容易把“题目”和“题目出现的位置”混在一起。未来应明确：

- `Question` 表示题目本身。
- `PaperQuestion` 表示“这个题目在这张试卷中的出现方式”。
- `TopicQuestion` 表示“这个题目在这个专题中的组织方式”。
- 文件路径只是导出视图或兼容层，不应继续作为唯一结构。

## 7. 与当前 MathCyclus 项目的差异

当前项目主要存储方式：

- 题目以 `.tex` 文件形式存放在 `chapters/<知识板块>/<年份>/...`。
- 文件中包含标签注释块：
  - `% === Begin Label Data ===`
  - `% ID`
  - `% 难度星级`
  - `% 标签`
  - `% 备注`
  - `% 组卷引用次数`
- 内容环境包括：
  - `\begin{problem}...\end{problem}`
  - `\begin{answer}...\end{answer}`
  - `\begin{solutions}...\end{solutions}`
- 搜索、索引、统计可能依赖 CSV、SQLite 或本地缓存。

当前方案优点：

- 直观，容易人工打开和编辑。
- 与 LaTeX 工作流兼容。
- 对小规模题库维护成本低。
- 文件可直接进入试卷排版链路。

当前方案的局限：

- 题目身份容易受文件名、路径、移动位置影响。
- 同一题多来源、多试卷出现时难以表达。
- 专题分组、排序、备注会和题目本体混杂。
- 批量导入时难以安全判断“是否覆盖人工修改”。
- 图片附件缺乏稳定挂接点。
- AI 规范化前后版本难以追踪。
- 未来如果支持教材习题、专题、试卷、错题、用户数据，会变得越来越难维护。

## 8. 推荐的未来数据模型草案

下面是为后续重构准备的概念模型，不要求一次性实现。

### 8.1 Question：题目本体

建议字段：

| 字段 | 说明 |
| --- | --- |
| `question_id` | 稳定唯一 ID，未来所有关系都引用它 |
| `stem_tex` | 题干 TeX |
| `choices_tex` | 选项结构，可 JSON 或拆 A~E |
| `answer_tex` | 标准答案 |
| `solution_tex` | 解析 |
| `difficulty` | 难度星级或数值 |
| `tags` | 标签，可拆成关系表 |
| `note` | 备注 |
| `question_type_id` | 题型 |
| `official_flag` | 是否官方答案/官方来源 |
| `raw_source_tex` | 原始导入文本 |
| `normalized_status` | 未规范化/已规范化/待人工确认 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `last_manual_edit_at` | 最近人工编辑时间 |

### 8.2 QuestionAnalysis：教研分析字段

如果字段较多，可以单独拆表：

| 字段 | 说明 |
| --- | --- |
| `question_id` | 关联题目 |
| `target_tex` | 考查目的 |
| `production_tex` | 命题过程 |
| `evaluation_tex` | 试题评析 |
| `marking_data_tex` | 阅卷数据 |
| `warning_tex` | 易错警示 |
| `reference_text` | 参考文献或来源说明 |

拆表好处是避免 `Question` 表过胖，也便于后续只加载核心题目而延迟加载教研字段。

### 8.3 Paper：试卷

建议字段：

| 字段 | 说明 |
| --- | --- |
| `paper_id` | 稳定唯一 ID |
| `year` | 年份 |
| `paper_name` | 标准试卷名 |
| `source_name` | 原始来源名 |
| `region` | 地区/卷别 |
| `track` | 文科/理科/新高考/全国卷等 |
| `description` | 说明 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 8.4 PaperQuestion：试卷题目关系

建议字段：

| 字段 | 说明 |
| --- | --- |
| `paper_question_id` | 关系 ID |
| `paper_id` | 试卷 ID |
| `question_id` | 题目 ID |
| `question_number` | 题号 |
| `liberal_arts_number` | 题号（文） |
| `sub_number` | 小题 |
| `display_order` | 试卷内排序 |
| `origin_tex` | 原始出处命令或来源文本 |
| `location_tex` | 位置信息 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

关键原则：

- 同一题在文理卷中出现，应建立两个 `PaperQuestion` 记录。
- 同一题跨多个地区或年份出现，也应建立多个关系记录。
- 题号不是题目的固有属性，而是题目在某张试卷中的属性。

### 8.5 TopicModule / Topic / TopicQuestion：专题系统

`TopicModule`：

| 字段 | 说明 |
| --- | --- |
| `module_id` | 大专题 ID |
| `name` | 大专题名称，如函数、解析几何 |
| `description` | 说明 |
| `sort_order` | 排序 |

`Topic`：

| 字段 | 说明 |
| --- | --- |
| `topic_id` | 小专题 ID |
| `module_id` | 所属大专题 |
| `name` | 专题名称 |
| `file_name` | 导出文件名 |
| `description` | 简介 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

`TopicQuestion`：

| 字段 | 说明 |
| --- | --- |
| `topic_question_id` | 关系 ID |
| `topic_id` | 专题 ID |
| `question_id` | 题目 ID |
| `group_name` | A组/B组/基础/提高等 |
| `sort_order` | 专题内排序 |
| `topic_note` | 该题在本专题中的备注 |

关键原则：

- 专题备注不应污染题目本体备注。
- 专题排序不应改变题目文件顺序。
- 题目可以同时属于多个专题，并在每个专题中有不同位置。

### 8.6 QuestionAsset：图片与附件

未来非 TikZ 图片应通过资源表挂接：

| 字段 | 说明 |
| --- | --- |
| `asset_id` | 资源 ID |
| `question_id` | 关联题目 |
| `asset_type` | image/pdf/source/vector 等 |
| `role` | problem/solution/explanation/thumbnail |
| `file_path` | 本地相对路径 |
| `original_file_name` | 原始文件名 |
| `mime_type` | 文件类型 |
| `width` / `height` | 图片尺寸 |
| `hash` | 文件哈希，用于去重 |
| `caption` | 说明 |
| `created_at` | 创建时间 |

建议目录结构：

```text
assets/
  questions/
    Q000001/
      problem-1.png
      solution-1.svg
      source-original.pdf
```

或者：

```text
assets/
  2025/
    Q000001/
      problem-1.png
```

更推荐按 `question_id` 管理，而不是按年份或知识板块管理，因为图片是题目资产，不是年份资产。

### 8.7 QuestionRevision：修订记录

建议字段：

| 字段 | 说明 |
| --- | --- |
| `revision_id` | 修订 ID |
| `question_id` | 题目 ID |
| `changed_fields` | 变更字段 |
| `before_snapshot` | 修改前快照 |
| `after_snapshot` | 修改后快照 |
| `change_source` | manual/ai_import/ocr/batch_normalize |
| `operator` | 操作者，可先留空 |
| `created_at` | 修订时间 |

意义：

- AI 批量修改可回滚。
- 可以判断某题是否被人工编辑过。
- 未来出现格式问题，可以追溯是哪次导入造成。

### 8.8 ImportBatch / ImportReportItem：批量导入报告

`ImportBatch`：

| 字段 | 说明 |
| --- | --- |
| `batch_id` | 批次 ID |
| `source_path` | 源路径 |
| `mode` | 试跑/正式导入 |
| `started_at` | 开始时间 |
| `finished_at` | 结束时间 |
| `summary` | 摘要 |

`ImportReportItem`：

| 字段 | 说明 |
| --- | --- |
| `item_id` | 报告项 ID |
| `batch_id` | 批次 ID |
| `source_file` | 源文件 |
| `paper_name` | 试卷名 |
| `question_number` | 题号 |
| `status` | inserted/updated/skipped/error/need_confirm |
| `reason` | 原因 |
| `last_update_date` | 原题更新时间 |
| `detail` | 详细说明 |

这对应朋友系统的导入要求：改了什么、跳过什么、哪些需要确认、哪些试卷不存在，都必须可回看。

## 9. AI 录入与规范化的推荐流程

未来无论录入试卷、专题还是教材，都建议采用下面流程：

1. **导入源文件**
   - 原始 `.tex`、PDF、图片、OCR 文本都先作为原始材料保存。
   - 不直接覆盖当前题库。

2. **结构解析**
   - 识别题号、题干、选项、答案、解析、来源、官方标记。
   - 不能稳定识别的内容进入待确认列表。

3. **映射确认**
   - 确认源试卷名与标准试卷名映射。
   - 确认专题目录、教材章节或年份归属。

4. **规范化**
   - 只处理白名单字段。
   - 保留原始 TeX。
   - 自动修正常见格式问题。
   - 特殊表格、复杂选项、图片题、非标准环境进入人工确认。

5. **预览校验**
   - 至少进行 KaTeX/MathJax 前端预览。
   - 对完整 LaTeX 导出场景可增加 `xelatex` 检查。
   - 校验失败不入正式库。

6. **冲突判断**
   - 题目不存在：插入。
   - 题目存在且未人工修改：可更新。
   - 题目存在且后续人工修改过：跳过并报告。

7. **报告确认**
   - 先展示导入报告。
   - 用户确认后再写入正式库。

8. **备份**
   - 每次正式导入前自动备份。
   - 备份文件名包含日期。
   - 同日多次备份使用 `_1`、`_2` 或类似后缀。

## 10. 对当前 UI 的未来启发

虽然本文档不修改当前代码，但后续 UI 可以参考以下方向。

### 10.1 录入新题

未来可以拆成四个稳定区域：

- 左侧：题目定位与元信息。
- 中间：题干、答案、解析、扩展字段编辑。
- 右侧：实时预览与校验结果。
- 底部：格式化、检查、AI 生成、OCR、保存、导出操作。

按钮状态应该明确：

- 未编辑状态：只能复制源码/查看预览。
- 点击“开始修改”后：源码可编辑，按钮变为“保存修改”。
- 保存后：写入记录，并退出编辑状态。
- AI 生成或图片识别应进入草稿，不应直接覆盖正式内容。

### 10.2 全局浏览与组卷

当前已经做过很多 UI 调整，未来重构时应保留这些原则：

- 大量题目不能一次性全部渲染，尤其 LaTeX 预览必须分页或虚拟滚动。
- 每页可选 `5 / 10 / 15 / 20`，默认不宜过大。
- 左侧导航和搜索条件可以吸附滚动，方便浏览第十题以后仍能切换。
- 组卷服务使用右侧悬浮试题篮，而不是占据页面正文。
- 试题篮内应支持：
  - 已选题目预览
  - 一次点击移除
  - 拖拽排序
  - 可调整大小
  - 默认不透明
  - 不因点击或排序触发整页刷新

### 10.3 搜索模式

搜索模式下左侧吸附栏可以包括：

- 退出检索按钮。
- 一级/二级/三级搜索条件竖排或紧凑单行排布。
- 再次搜索按钮。
- 查找结果摘要，例如“找到 229 个匹配题目”。
- 每页显示数量与当前页码。

右侧主区域只展示题目结果，不重复显示过多统计标题。

## 11. 图片与非 TikZ 图的策略

用户已经提出未来要考虑“非 TikZ 的图在问题及其解答中的插入与前端显示”。结合存储大修计划，建议不要现在立即把图片功能硬塞进旧结构。

原因：

- 如果没有稳定 `question_id`，图片只能挂在文件路径上，后续移动题目会很麻烦。
- 如果题目拆分方式改变，图片引用路径可能需要二次迁移。
- 如果未来支持一题多版本、一题多来源，图片属于哪一版也需要明确。
- 图片 OCR、裁剪、压缩、前端预览、LaTeX 导出是一个完整子系统，不应临时拼接。

建议顺序：

1. 先确定新题库数据模型。
2. 确定 `question_id` 和资源目录规则。
3. 增加 `QuestionAsset` 概念。
4. 再实现前端插图能力。

图片功能初版可以支持：

- 上传图片到题目资源目录。
- 选择图片用途：题干图、解析图、答案图、缩略图。
- 在 TeX 中插入占位命令，例如 `\includegraphics{...}` 或自定义 `\questionimage{asset_id}`。
- 前端预览时解析并显示图片。
- 导出 LaTeX 时把图片复制到目标目录并修正相对路径。

长期还可以支持：

- 图片哈希去重。
- 图片压缩和尺寸记录。
- SVG/PDF/PNG/JPG 多格式。
- 原图与裁剪图同时保存。
- AI 根据图片生成描述文本，辅助检索。

## 12. 迁移策略建议

当前项目已经能用，不建议一次性推翻重写。更稳妥的路线是“兼容层 + 增量迁移”。

### 阶段一：盘点现状

- 扫描所有 `.tex` 文件。
- 提取现有 ID、难度、标签、备注、组卷引用次数。
- 统计缺失 ID、重复 ID、格式异常、无法解析的问题。
- 输出报告，不改文件。

### 阶段二：建立稳定题目索引

- 给每道题建立稳定 `question_id`。
- 生成 `questions_index.sqlite` 或类似数据库。
- 保留原文件路径作为 `source_file_path`。
- 旧 UI 继续读 `.tex`，新功能优先读索引。

### 阶段三：拆分关系

- 从文件路径和题干来源中提取年份、试卷、题号。
- 建立 `Paper` 与 `PaperQuestion`。
- 建立专题模块、专题和专题题目关系。
- 逐步减少对目录结构的业务依赖。

### 阶段四：引入修订和导入报告

- 所有 AI/OCR/批量规范化写入 `QuestionRevision`。
- 批量导入必须生成 `ImportBatch` 和 `ImportReportItem`。
- 正式写入前自动备份。

### 阶段五：图片附件系统

- 引入 `QuestionAsset`。
- 支持上传、预览、TeX 插入、导出。
- 对旧题中的图片路径进行迁移或映射。

### 阶段六：逐步重构 UI

- 当前 Streamlit 可以继续作为管理端。
- 核心逻辑抽到 service 层。
- 存储读写通过统一接口，不让页面直接解析文件。
- 如果未来要换 H5 + localhost，也可以复用服务层和数据模型。

## 13. 需要避免的风险

### 13.1 不要让 AI 直接覆盖正式题库

AI 可以辅助解析、格式化、生成答案、识别图片，但正式写入必须经过校验和报告。

### 13.2 不要把所有字段都塞回 TeX 注释

TeX 文件适合表达题目内容，但不适合长期承载所有关系型数据。比如专题排序、试卷关系、导入批次、图片资源、修订记录，都更适合数据库或结构化索引。

### 13.3 不要过早设计复杂后台

当前最重要的是先把数据模型设计清楚。是否使用 SQLite、SQL Server、PostgreSQL、DuckDB 或文件索引，可以后续再定。对个人本地题库而言，SQLite 很可能已经足够。

### 13.4 不要急着做图片功能

图片功能依赖稳定 ID 和资源目录。应先完成存储结构设计，否则未来迁移成本会很高。

### 13.5 不要让 UI 状态和数据状态混在一起

例如组卷篮里的排序、分页选择、搜索条件、试题预览展开状态，应属于 UI/session 状态；题目内容、标签、难度、备注、试卷关系才属于持久数据。

## 14. 后续讨论清单

后续正式设计题库格式时，建议逐项讨论：

1. 是否继续以 `.tex` 文件作为主存储，还是改为 SQLite 主存储、TeX 作为导出格式。
2. `question_id` 的命名规则：数字、自增、UUID、带年份前缀，还是保留现有 ID 并补齐。
3. 当前 `chapters/<知识板块>/<年份>` 是否继续作为物理目录，还是变成一种分类视图。
4. 难度、标签、备注是否继续写入 TeX 注释，还是迁移到结构化索引。
5. 试卷来源如何标准化：年份、卷别、地区、文理、新高考、模拟卷、教材。
6. 同一道题跨多张试卷出现时，如何判断“同题”。
7. 专题系统是否作为一等对象实现，而不是只靠标签。
8. 图片资源目录和 TeX 引用方式如何设计。
9. AI 录入的“草稿区”和“正式库”是否分开。
10. 批量导入报告、备份、回滚如何落地。
11. 未来是否需要用户维度，例如错题、收藏、做题记录、掌握度。
12. 未来是否需要版本维度，例如官方解析、个人解析、AI 解析、多种解法。

## 15. 初步结论

朋友系统最值得借鉴的不是某个页面样式，而是它把题库看成了结构化业务系统：

- 题目是题目。
- 试卷是试卷。
- 专题是专题。
- 题目出现在试卷中的位置是关系。
- 题目出现在专题中的顺序、分组和备注也是关系。
- AI 导入必须有检查、规范化、报告和备份。
- 原始材料与规范化结果必须分开。

对 MathCyclus 来说，下一轮大修的核心不是先做更复杂的 UI，而是先建立稳定的数据模型。只要 `question_id`、试卷关系、专题关系、附件资源和修订记录这几层设计清楚，后续的录入页面、全局浏览、组卷服务、图片插入和 AI 批量导入都会更稳。
