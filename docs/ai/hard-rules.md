# AI 与开发硬规则

## 1. 数据安全

- 不读取、打印或提交 `.env`、API Key、个人路径和本地授权信息。
- 不把 `data/`、`assets/questions/`、`reports/`、`exports/`、真实 PDF、旧题源和本地数据库加入 GitHub。
- 不因整理目录而删除数据库、题目、备份、PDF、图片或不确定的维护脚本。
- 运行可能写库、删题、合并题目、拆分题目或同步旧 TeX 的操作前，必须先备份并保留 dry-run/审计结果。

## 2. 架构边界

- SQLite 是当前结构化题库主存储；旧 `.tex` 是兼容来源、人工可读备份和导出目标。
- UI 层不能绕过服务层直接拼接数据库写操作。
- AI/OCR、PDF 和本地 Codex 的识别结果先进入草稿或任务目录，不能绕过人工审核写正式题库。
- 保持现有 Streamlit UI 和旧 TeX 兼容流程稳定，不因局部优化大规模重写主入口。

## 3. 题目身份与关系

- 题目身份使用稳定 `question_id`，不能用年份、题号、文件名替代。
- “同一试卷、年份、卷别、文理/赛道、题号”是来源位置冲突；它不等于题干重复。
- “题干完全相同”“高度相似”“变式题”是内容关系，必须与来源位置冲突分开处理。
- 不自动删除或合并疑似重复题；优先建立可审核的关系记录。

## 4. 修改与验证

- 先读现有代码和相关文档，再决定是否抽象或重构。
- 手工编辑文件使用 `apply_patch`；不使用破坏性 Git 命令覆盖用户已有改动。
- 修改前说明影响范围；修改后至少运行编译检查和对应 smoke。
- 发现失败时区分功能失败、数据 warning、工作区未提交改动和环境缺失，不用删除改动来消除 warning。
- 文档中明确区分“当前实现”“当前待办”和“历史记录”。
